4aud vs audience vs resource vs issuer

Four things that all sound like "who is this for." Getting them right is most of the battle:

"aud" CLAIM (inside a JWT) — points ONE HOP DOWNSTREAM from whoever signed it:
   client_assertion  →  aud = the TOKEN ENDPOINT you are POSTing to        (RFC 7523)
   id-JAG            →  aud = the RESOURCE AUTHORIZATION SERVER's identifier
   access token      →  aud = the audience value configured on that AS

"audience" BODY PARAM (RFC 8693) — in the T2 exchange REQUEST: names the AS that
   must ACCEPT the id-JAG.  Here: the resource AS's own issuer URL
   https://ntrsoiesys.oktapreview.com/oauth2/aus10ta4mhvArN8jE1d8
   NOT api://something — a real bug we hit.

"resource" BODY PARAM (RFC 8707) — names the specific protected RESOURCE.
   In STS/secrets flows it's an Okta ORN selecting WHICH resource connection:
   orn:oktapreview:idp:<org-id>:client-auth-settings:<connection-id>

ISSUER ("iss") — who minted the token. Validators pin it exactly and fetch
   that issuer's JWKS to verify the signature.
Rule of thumb: aud inside a JWT points one hop downstream from the signer; audience and resource in a request body tell the AS what to mint.

5Anatomy of a client_assertion

Every privileged call authenticates with private_key_jwt (RFC 7523) — the agent never holds a client secret. It signs this JWT itself:

Header:  { "alg": "RS256", "kid": "<AGENT_KID — must match the JWK registered in Okta>" }
Payload: {
  "iss": "wlp10tv4ror3uKEbH1d8",   // the agent IS the issuer…
  "sub": "wlp10tv4ror3uKEbH1d8",   // …and the subject: self-attestation
  "aud": "https://ntrsoiesys.oktapreview.com/oauth2/v1/token",  // the EXACT endpoint
  "iat": 1751800000, "exp": 1751800300,   // short — minutes, not hours
  "jti": "random-unique-id"            // replay protection
}
// rides in the POST body:
client_assertion_type = urn:ietf:params:oauth:client-assertion-type:jwt-bearer
client_assertion      = <the signed JWT>

Okta verifies it against the public JWK registered on the agent. Three real failure modes: no JWK registered (invalid_client: no JWKSet), kid mismatch, and wrong aud — which must equal the endpoint you call (token endpoint for exchanges, revoke endpoint for revocations).

POST https://ntrsoiesys.oktapreview.com/oauth2/v1/token (form-urlencoded):

requested_token_type…:token-type:id-jag"give me an Identity Assertion Authorization Grant"

Okta checks policy — is this agent allowed token-exchange toward this audience, with a Resource Connection? — then mints:

Header:  { "typ": "oauth-id-jag+jwt", "alg": "RS256" }
Payload: {
  "iss": "https://ntrsoiesys.oktapreview.com",     // org AS minted it
  "sub": "<user id>",                              // the HUMAN
  "aud": "https://…/oauth2/aus10ta4mhvArN8jE1d8",  // the resource AS
  "client_id": "wlp10tv4ror3uKEbH1d8",             // the AGENT
  "scope": "inventory:read", "jti", "iat", "exp"   // short-lived
}
Reading trap: the response carries the id-JAG in access_token with token_type: N_A. An id-JAG is not an access token — you can't call an API with it; redeem it at the AS named in aud.

T3 — redeeming the id-JAG (jwt-bearer)

POST https://…/aus10ta4mhvArN8jE1d8/v1/token with grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer, assertion=<id-JAG>, plus a fresh agent client_assertion whose aud is this endpoint. The resource AS validates the id-JAG's signature against the org AS JWKS, checks aud == itself, applies its access policy, and mints the final access token (iss = resource AS, sub = user, agent identity carried, scp: ["inventory:read"]).

Platform reality (July 2026): Okta's org id-JAG exchange accepts only id_token/saml2 subjects. An access-token subject returns invalid_request: 'subject_token_type' is invalid or not supported. The request is correct per RFC 8693 — the platform doesn't yet accept a workload as the subject. Okta's EA notes point toward service-app-without-user-context support; the demo degrades gracefully at T2 meanwhile.

Two different keys authenticate here: T1 is signed by the service key (proves the workload), T2/T3 by the agent key (proves the agent). Keep them distinct.

The brokered gho_… token is GitHub's, not Okta's — opaque, provider lifetime, scopes governed by the Resource Connection. The agent never sees the GitHub client secret; that lives in the OIN app's Sign-On → Client authentication settings.

Behind the scenes — two separate OAuth conversations

The flow is really two OAuth conversations that never touch, and Okta is the only party in both. GitHub never learns an agent exists — it sees an ordinary OAuth-app authorization in which Okta itself is the OAuth client.

Conversation A — agent ↔ OktaConversation B — Okta ↔ GitHub
ProtocolRFC 8693 token exchange + RFC 7523 client_assertionplain OAuth 2.0 authorization-code flow
Client credentialagent private key (keys/agent.pem)GitHub client_id + secret vaulted in the OIN app
Carried byserver-to-server POSTs from the appthe user's browser (redirects) + Okta's back-channel (code exchange)
Who sees whatagent sees only interaction_uri and, later, gho_…agent sees nothing — no code, no secret, no refresh token

What happens when the user opens interaction_uri — all of it on Okta's side; the demo app is not involved:

  1. The URI lands on an Okta-hosted consent page (riding the user's existing Okta session): "Agent X wants to access GitHub on your behalf."
  2. On approval, Okta (not the app) redirects the browser to github.com/login/oauth/authorize?client_id=<OIN app's GitHub client_id>&redirect_uri=https://<okta>/oauth2/v1/sts/callback&state=…
  3. The user approves on GitHub's page; GitHub redirects the browser back to Okta's callback with ?code=…
  4. Okta exchanges the code back-channel at github.com/login/oauth/access_token, authenticating with the vaulted client secret → receives gho_… and vaults it keyed by user × connection.
  5. Nothing is returned to the agent. The retry succeeds because consent is server-side state inside Okta — which is exactly why re-sending the byte-identical T2 request gets a different answer.
Where the app's code stops: the app's only communication with Okta in this flow is two authenticated POSTs — T2 to /oauth2/v1/token and R1 to /oauth2/v1/revoke (server/xaa/stsBroker.js). The interaction_uri arrives as plain JSON in the 400 body; the React UI just renders it as an Authorize ↗ link (Chat.jsx) and the browser takes it from there. The app hosts no OAuth callback for GitHub — the only callback registered on the GitHub OAuth app is Okta's own /oauth2/v1/sts/callback.

MCP mechanics worth knowing

  • Responses may arrive SSE-framed (Content-Type: text/event-stream) — the JSON-RPC reply is the last data: line.
  • JSON-RPC errors ride on HTTP 200 — check for an error member; HTTP status alone lies.
  • Mcp-Session-Id from initialize must be echoed on every later call.

7The consent loop (interaction_required)

  1. T2 first attempt → HTTP 400 {"error":"interaction_required","interaction_uri":"…"}. Okta has no vaulted provider token for this user × connection yet.
  2. The UI shows Authorize connection ↗ (opens interaction_uri) and Retry.
  3. On the consent page Okta runs the provider's authorization-code flow — the provider redirects back to https://<okta-domain>/oauth2/v1/sts/callback (this exact URL must be registered on the provider OAuth app). Okta vaults the provider token server-side.
  4. The agent retries the byte-identical request → HTTP 200. No new parameter, no code handed to the agent — the state change happened entirely inside Okta.
Security property: the agent never participates in the provider's OAuth dance and never sees the provider client secret or refresh token. Consent is per user × per connection, auditable, and revocable. In traffic terms: the app server exchanges only two POSTs with Okta (token-exchange and revoke); the entire consent redirect chain runs browser ↔ Okta ↔ provider, with the app out of the loop.

Code-side vs Okta-side — exactly who does what

What your code does (the only app ↔ Okta communication):

  1. stsBroker.js sends one POST to https://<org>/oauth2/v1/token (the token-exchange). That's a server-to-server HTTPS call authenticated with the agent's private key.
  2. On first run, Okta answers 400 with a JSON body containing interaction_uri. The code (stsBroker.js:45) just plucks that string out of the JSON — it's data, not a redirect.
  3. routes/ask.js passes it to the UI, and Chat.jsx renders it as the Authorize ↗ link (<a href={interaction.uri} target="_blank">). Opening it is a plain browser navigation initiated by the user's click.
  4. Later, one more POST for revoke (/oauth2/v1/revoke). That's it — two POSTs total; the app server never talks to GitHub's OAuth endpoints at all.

What Okta does (everything after the click): the interaction_uri points at an Okta-hosted consent page. When the user approves, it's Okta's web server that issues the HTTP 302 sending the browser to github.com/login/oauth/authorize — with Okta's stored GitHub client_id and redirect_uri=https://<okta>/oauth2/v1/sts/callback. GitHub sends the browser back to Okta's callback with the authorization code, and Okta exchanges that code for gho_… back-channel using the client secret vaulted in the OIN app. The app hosts no callback route for any of this — the only GitHub callback that exists is Okta's.

The tell-tale proof it's out-of-band: the agent's retry is the byte-identical request. If the app's code were part of the dance, the retry would have to carry something new (a code, a session, a nonce). It doesn't — the state change happened entirely inside Okta's vault.

What is the interaction_uri, actually? A URL on your own Okta org's domain (e.g. https://<org>.oktapreview.com/…), minted by Okta at the moment it returns the 400. Its path carries an opaque one-time handle that Okta maps server-side to the pending grant request (user × resource connection × agent) — the URI itself contains no GitHub parameters. Okta "gets" it from nowhere: it creates the pending-consent record and the URI together, from what the T2 request already told it — subject_token = which user, resource ORN = which connection, client_assertion = which agent. To see a real one, run the STS flow and check the T2 Response tab (or set DEBUG_FLOWS=1).

8Revocation (RFC 7009)

POST https://<org>/oauth2/v1/revoke
  token                 = <the brokered access token>
  token_type_hint       = oauth_sts
  client_assertion_type = urn:ietf:params:oauth:client-assertion-type:jwt-bearer
  client_assertion      = agent key — aud = the REVOKE endpoint, not the token endpoint!

Revoking an STS token deletes Okta's vaulted grant → the next T2 returns interaction_required again. That's revocation precision: kill one user's one connection without touching anything else. XAA needs no equivalent — id-JAGs and access tokens simply expire in minutes; revoke by disabling the agent or its resource connection.

9Proving the managed connection

"How do we know the agent isn't just using a hidden GitHub token?" — the question every security review asks about the broker flows. Six pieces of evidence; for a live demo run 2 → 1 → 3 → 5 (about two minutes).

  1. The T2 request names the connection on the wire. The step card's Request tab shows resource=orn:…:client-auth-settings:<connection-id> — the exact ORN on the AI Agent's Resource Connections tab — sent to Okta's token endpoint, authenticated only by the agent's client_assertion.
  2. The codebase holds no provider credential. grep -ri "gho_\|ghp_\|GITHUB_TOKEN" server/ .env → nothing. The only GitHub secret is the OAuth app's ID/secret, stored inside Okta where the agent cannot read it. If the agent still reaches the resource, the token must have come from Okta.
  3. The revoke test (strongest live proof). Revoke, re-run → interaction_required. Nothing changed locally or at the provider; only Okta's vaulted grant was deleted, and access died instantly.
  4. The kill switch. Deactivate the Resource Connection (or credential set) in Okta Admin → the byte-identical request fails, code and keys untouched. Re-enable → works. IT-controlled, per-connection revocation.
  5. The Okta System Log. Reports → System Log, filter client.id eq "<wlp… agent id>": every grant shows actor = agent, subject = user, target = the resource connection, timestamped per run — compliance-grade attribution.
  6. The provider agrees. GitHub → Settings → Applications → Authorized OAuth Apps shows the grant created at the consent click, and get_me returns that user's identity — the token carries the consenting user's delegation, not a bot account.

10Validation at the resource (T4)

The Inventory MCP shows the non-negotiable checklist every resource must run (server/util/verifyToken.js):

  1. Fetch JWKS from the expected issuer's jwks_uri and verify the signature.
  2. Pin iss — exact string match against the resource AS.
  3. Check exp (with reasonable clock skew).
  4. Enforce scopes: scp must contain inventory:read → else 403 insufficient_scope.
  5. Signature / issuer / expiry failure → 401 invalid_token.
Decode ≠ verify. The client-side JWT viewer in the demo deliberately does no signature check — display only. Never authorize off an unverified decode.

11Security principles for agent builders

  1. No static secrets on the agent. One RSA private key; everything else is minted per-request and short-lived.
  2. Identity chain, not identity collapse. XAA carries user and agent at every hop → per-user audit, surgical revocation. Every step toward service-account sharing loses attribution.
  3. Scope narrowing at every exchange. Effective access = agent capabilities ∩ user entitlements ∩ requested scope.
  4. Short lifetimes limit blast radius. Assertions in minutes, access tokens ≤ 1 h, id-JAGs single-purpose.
  5. aud pinning everywhere. A token replayed anywhere but its intended endpoint fails.
  6. The IdP is the policy chokepoint. Resource Connections + access policies + the consent vault control which agent reaches which resource as which user — no agent code changes.
  7. Resources verify, never trust. JWKS + iss + exp + scope at every resource; HTTP success ≠ protocol success (MCP's error-on-200).
  8. Choose the strongest pattern the resource supports: XAA > STS > PSK > Service Account.
